# Обзор проекта и план развития — issue #1

## Результат разбора

Проект из `tochki-multiplayer-main.zip` развёрнут в корне репозитория:
исходники, клиент, зависимости с lockfile, тесты и инструмент обучения.
Архив оставлен как исходный материал. Алгоритмы игры при распаковке не
переписаны: это задача анализа и планирования, а не заявление об уже
усиленном боте или готовом offline-клиенте.

Два главных направления разобраны отдельно:

- [Почему бот играет локально и как его усиливать](BOT_ANALYSIS.md).
- [Вариант игры без backend: человек–бот и бот–бот](OFFLINE_PLAN.md).

Исторический README описывает предыдущие этапы разработки. Упоминания там
старого однопользовательского `tochki_2_2_.html` не означают, что такой файл
присутствует в распакованном проекте.

## Карта системы

| Файлы | Роль и вывод |
|---|---|
| `gameEngine.js` | Общий движок правил, создание независимых матчей, захваты, завершение игры, оценка позиции и поиск бота. Самая ценная граница для переиспользования offline, но правила, эвристики и поиск пока сосредоточены в одном модуле. |
| `server.js` | HTTP API, WebSocket, комнаты, подбор соперников, переподключение, зрители, реванши, отмена хода, интеграция БД и запуск обучения. Авторитетное состояние находится здесь; крупный модуль усложняет изолированную проверку жизненного цикла комнаты. |
| `public/client.html` | UI, canvas, сетевой протокол и локальное отображение состояния в одном HTML. Это сетевой клиент, не готовая бессерверная игра. Для offline нужно отделить управление матчем от транспорта, а не просто убрать подключение WebSocket. |
| `db.js` | SQLite-схема и хранение пользователей, сессий, партий, ходов, весов. Удобно для одного процесса; нужен постоянный диск, резервирование и явная стратегия миграций. |
| `auth.js` | Регистрация, проверка уникальности, scrypt-пароли, сессии. Хэширование не заменяет TLS и защиту публичного входа от перебора. |
| `gamelog.js` | Запись партий/ходов, статистика, выбор дебютов для обучения и хранение весов. История завершённых партий и восстановление активной комнаты — разные задачи. |
| `tools/train-bot.js` | Эволюционный подбор весов эвристик через self-play. Не обучение нейросети и не освоение стратегии по всем человеческим ходам. Сила зависит от поискового алгоритма и качества контрольных соперников, а не только от количества прогонов. |
| `package.json`, `package-lock.json`, `.node-version` | Запуск и воспроизводимые зависимости. `better-sqlite3` — нативный модуль: проверять совместимость выбранной версии Node, а не считать любой установленный Node подходящим. |
| `test/*.js` | Семь интеграционных сценариев. Хорошая проверка сетевых функций, но не доказательство стратегической силы бота или полноты правил захвата. |

### Потоки данных

1. Клиент посылает запрос; сервер проверяет место игрока и состояние комнаты.
2. Матч применяет ход; сервер пишет лог и рассылает snapshot игрокам/зрителям.
3. В комнате с ботом сервер отдельно вызывает синхронный поиск и применяет ответ.
   Задержка через таймер сама по себе не переносит CPU-работу в другой поток.
4. Обучение запускается отдельным дочерним процессом; новые веса попадают в
   SQLite и подхватываются при последующих ходах. Это изолирует обучение от
   event loop, но не устраняет конкуренцию процессов за CPU.

## Архив и данные

В архивной `data/tochki.db` при распаковке обнаружены 14 записей партий и
8 ходов; пользователей, сессий и сохранённых весов бота не было.
Это небольшой исторический набор, не убедительная обучающая или
контрольная выборка. Бинарная БД не перенесена в рабочее дерево:
проект создаёт новую через `db.js`, локальные данные исключены `.gitignore`.
Исходный экземпляр остаётся внутри сохранённого ZIP; это осознанное
исключение из распаковки, а не потеря необходимого исходного кода.
Если понадобятся именно эти записи, извлекать БД отдельно, в новый путь,
не поверх текущей рабочей БД, и задавать `DB_PATH`.

## Основные риски и границы доказанного

- **Цель бота.** Формально максимизировать эвристическую оценку не то же
  самое, что максимизировать вероятность победы по правилам матча.
  Сначала нужно устранить расхождения симуляции с матчем, затем измерять
  стратегию. Подробности и привязки к функциям — в BOT_ANALYSIS.
- **Горизонт и кандидаты.** Увеличение глубины не поможет, если глобальный
  ход отбрасывается до поиска. Нужно отдельно проверять качество набора
  кандидатов и оценки долгосрочного окружения.
- **Производительность.** Синхронный поиск блокирует обслуживание других
  комнат. Нужны измерения задержек и изоляция вычислений; лимит времени
  поиска нельзя трактовать как гарантию полной задержки запроса.
- **Надёжность.** Комнаты, места, таймеры и сокеты живут в памяти. Наличие
  логов в SQLite не означает автоматического восстановления партии после
  рестарта. Определить политику незавершённых партий и восстановления.
- **Эксплуатация.** Перед публичным запуском отдельно проверить ограничения
  HTTP/WS-запросов, rate limiting регистрации/входа и создания комнат,
  доступ к логам по коду, открытые сводки обучения и жизненный цикл токенов.
  Это список аудита, не утверждение, что проведён полноценный pentest.
  Запуск обучения уже защищён `ADMIN_TOKEN`; read-only сводки — нет.
- **UX и анализ.** Монолитный клиент удобен как прототип, но для сравнения
  ботов нужны пауза, шаг, replay, версии правил и весов, а не только canvas.
- **Документация.** Старый README содержит исторические утверждения о силе
  бота; они не являются результатами нового сравнительного эксперимента.

## Единый порядок работ

Оценки ниже — относительный объём, не обещание сроков.

| Этап | Объём | Результат и критерий приёмки |
|---|---|---|
| 0. Воспроизводимая база | Малый | Зафиксировать поддерживаемый Node, прогнать семь интеграционных сценариев, сохранить исходного бота как контроль. Отдельно зафиксировать найденные сбои окружения. |
| 1. Контракт правил | Средний | Версионированные правила, позиции-фикстуры для захвата/освобождения, легальности, окончания и undo. Одинаковая последовательность ходов даёт одинаковые доску, счёт и результат в матче и поисковой симуляции. |
| 2. Offline-лаборатория | Средний | Переиспользовать движок, сделать локальный контроллер и Worker. Человек–бот и бот–бот, пауза/шаг/сброс, экспорт и импорт replay; никакого WS/API/SQLite. См. OFFLINE_PLAN. |
| 3. Контроль силы | Средний | Корпус тактических и стратегических позиций; фиксированные seeds, смена цветов, одинаковый бюджет вычислений, отдельная контрольная выборка. Отчёт по результатам партий, доле решённых позиций и времени хода. |
| 4. Усиление бота | Большой, итерациями | Терминальная цель, срочные и глобальные кандидаты, оценка окружения и жизнеспособности групп, затем поиск. Каждую идею проверять отдельно против базы; не принимать изменения только по красивой одиночной партии. |
| 5. Подбор весов | Средний | После стабилизации правил/признаков — self-play с пулом соперников, отделение обучения от проверки, версия весов и возможность отката. Победа над одним предыдущим кандидатом недостаточна для публикации весов. |
| 6. Сетевой продукт | Большой, независимо от offline | Worker для серверного бота, нагрузочные проверки, восстановление партий, backup БД, аудит API, затем история/статистика и финальный UI. |

Первый полезный цикл: **правила → локальная лаборатория → измерение →
одно улучшение → сравнение**. Он отвечает на обе главные просьбы issue:
делает цель бота проверяемой и позволяет наблюдать ботов без игрового сервера.
Полная перепись сетевой части или внедрение нейросети до этого цикла не нужны.

## Проверки распакованного проекта

В Codespaces на Node `v24.21.0`, npm `11.19.0` выполнен `npm ci`:
установка успешна, audit сообщил 0 уязвимостей (это не аудит безопасности
приложения). Далее успешно завершились:

```sh
node test/e2e.js
node test/auth.js
node test/names.js
node test/gamelog.js
node test/rooms.js
node test/undo.js
```

`node test/train.js` прошёл проверки защиты API и старта процесса, но
дочерний процесс упал в нативном `better-sqlite3`:
`node::RemoveEnvironmentCleanupHook`, assertion `(env) != nullptr`,
`Statement::~Statement()`. Итог теста — exit 1, а не успешное обучение.
Повторная проверка на версии из `.node-version` — Node `v20.13.0`,
npm `10.5.2`: `npm ci` успешен, audit сообщил 0 уязвимостей.
Выполнен полный `npm test`: `e2e`, `auth`, `names`, `gamelog`, `rooms`
прошли, но `train` завершился с `training did not finish within timeout`.
Это внутренний лимит ожидания 30000 мс в `test/train.js`, не таймаут
команды Codespaces. Из-за цепочки `&&` тест `undo` в этом запуске не
выполнялся; его успешный результат выше относится к Node 24.

Таким образом, весь `npm test` **не зелёный**; завершение обучения и
сохранение его результата в этом окружении не подтверждены. Сбой
зафиксирован отдельно в [issue #2](https://github.com/mlaa4ml/tochki-multiplayer/issues/2)
с командами воспроизведения и критериями исправления. Причинная связь
нативного сбоя на Node 24 и таймаута на Node 20 не установлена.
Исправление архивного обучения выходит за рамки распаковки и плана
в issue #1; оно должно войти в этап 0 до экспериментов с силой бота.
Версия Node из архива воспроизводит исходное окружение, но сама по
себе не является рекомендацией для нового production-развёртывания:
нужно выбрать поддерживаемую LTS и проверить нативные зависимости.

Ручная браузерная проверка и сравнительный турнир ботов пока не проводились.
Предложенные новые проверки силы и offline-функции — план дальнейшей
разработки, не функции этой ветки.
