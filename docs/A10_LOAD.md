# A10: изоляция серверного поиска бота и нагрузочная проверка (issue #15)

## Что было

`server.js` вызывал `match.botMove(...)` синхронно в `setTimeout`. Поиск
`strong` занимает около своего бюджета (до ~2000 мс), и всё это время общий
event loop процесса был заблокирован: стояли WS-сообщения и HTTP-запросы
**всех** комнат. Задержка `BOT_MOVE_DELAY_MS` лишь откладывала начало
блокировки, но не переносила CPU-работу в другой поток.

## Что сделано

- `botPool.js` — ограниченный пул `worker_threads`. Точка входа потока —
  существующий `botWorker.js`, поиск — тот же `gameEngine.searchMove`, что
  и у CLI, offline и `match.botMove`. Отдельной копии правил нет.
  - Предел параллелизма `size` (по умолчанию **2** потока). Потоки создаются
    лениво и переиспользуются, отдельный worker на каждый запрос не создаётся.
  - Ограниченная очередь `maxQueue` (по умолчанию **16**). При переполнении
    запрос сразу отклоняется с `code='queue-full'` (backpressure).
  - Жёсткий таймаут `timeoutMs` (по умолчанию **10000 мс**) считается от
    начала расчёта в потоке. По таймауту поток завершается через
    `terminate()` и пересоздаётся.
  - Падение потока (`error`/`exit`) отклоняет только его текущий запрос
    (`worker-crashed`), а пул продолжает работать.
  - `cancel(key)` снимает задачу из очереди или прерывает идущий расчёт.
  - `close()` отклоняет все задачи и дожидается завершения всех потоков.
    Простаивающие потоки помечены `unref()` и не держат процесс.
- `server.js`
  - На каждую комнату создаётся не больше одного активного «билета» поиска
    (`room.botTicket`). В поток уходит полный `getSnapshot()` (позиция,
    правила, `current`, `stonesPlacedTotal`, `gameOver`), а также `gameId`,
    `revision` (длина `moveLog`) и `requestId`.
  - Результат поиска применяется, только если одновременно выполнены все
    условия:
    - комната та же и не удалена;
    - билет текущий;
    - `room.match` и `gameId` те же (не было реванша);
    - `revision` не изменилась (не было undo или другого хода);
    - партия не окончена;
    - фактический `current === botSeat`.

    После этого ход всё равно проходит авторитетный `applyMove`.
    Следующий ход бота определяется по фактическому `current`, поэтому
    `extraTurnOnCapture` даёт ещё один поиск.
  - Undo, `end`, реванш и удаление комнаты (`onRoomExpired`) снимают поиск
    через `cancelBotSearch`. Даже если ответ успеет прийти, проверка выше
    его отбросит.
  - Ошибки `queue-full`, `timeout` и `worker-crashed` обрабатываются так:
    до 2 повторов с паузой 250 мс, затем запасной синхронный поиск с малым
    бюджетом (`nodeLimit 1500`, `timeLimit 150`). Партия не зависает и не
    повреждается.
  - `server.close()` и сигналы SIGINT/SIGTERM при запуске `node server.js`
    закрывают WS/HTTP и пул. После остановки потоков не остаётся.
    Закрытие `httpServer` тоже закрывает пул.
  - Жизненный цикл дочернего процесса обучения (#2) не менялся.

### Настройки

| Параметр | env | `createServer({ botPool })` | По умолчанию |
|---|---|---|---|
| Число потоков поиска | `BOT_POOL_SIZE` | `size` | 2 |
| Длина очереди | `BOT_QUEUE` | `maxQueue` | 16 |
| Таймаут поиска, мс | `BOT_TIMEOUT_MS` | `timeoutMs` | 10000 |

`BOT_POOL_SIZE=0` включает прежний синхронный режим. Он оставлен только для
замера «до» и для аварийного отката.

Рекомендация: `size` ≤ числа ядер − 1. Так основной поток сервера
сохраняет своё ядро. При 2 ядрах значение 2 — уже верхний предел.

## Заранее зафиксированный бюджет

Бюджет задан для **человеческой** комнаты при параллельной нагрузке ботами:

- WS RTT p95 ≤ **100 мс**;
- HTTP RTT p95 ≤ **150 мс**;
- event-loop lag p99 ≤ **100 мс**.

Число одновременных поисков ограничено `size` (2), ещё до 16 ждут в
очереди. Время ответа самого бота в бюджет не входит. При N комнатах со
`strong` и `size` потоках ожидаемое время ответа ≈ ⌈N/size⌉ × бюджет
`strong`.

## Как запустить нагрузочную проверку

```
npm ci
npm run load:bot
# или с параметрами:
node tools/load/bot-latency.js --rooms 4 --strong 2 --seconds 20 --pool-size 2 \
  [--mode sync|pool|both] [--probe-ms 100] [--out tools/load/reports/a10-bot-latency.json]
```

Сценарий:

- поднимается сервер с `:memory:` БД;
- создаются `--rooms` комнат с ботом (`--strong` из них — strong, остальные —
  normal, поле medium). «Человек» в них ходит сразу, как только ход за ним;
  после конца партии запускается реванш;
- параллельно работает отдельная человеческая комната из двух клиентов.
  Её клиент каждые `--probe-ms` измеряет WS RTT (`list-rooms` →
  `room-list`) и HTTP RTT (`GET /`);
- снимаются event-loop lag (`monitorEventLoopDelay`), CPU процесса (включая
  потоки), максимум RSS/heap, статистика пула (очередь, занятость, таймауты,
  падения) и время ответа бота.

Режим `both` прогоняет `sync` («до») и `pool` («после») подряд. Прогон длится
примерно 2 × `--seconds` плюс ~5 с.

На что смотреть в выводе:

- строка `budget=OK/EXCEEDED`;
- `loopLag p99`;
- `queueMax` — не должен упираться в `maxQueue`;
- `bot p95` — отражает рост времени ответа при очереди.

## Результаты (Codespace, 2 vCPU, Node 24)

`--rooms 4 --strong 2 --seconds 20 --pool-size 2`, полный отчёт:
`tools/load/reports/a10-bot-latency.json`.

| Показатель | sync (до) | pool (после) |
|---|---|---|
| WS p50 / p95 | 2,1 / 3,9 мс | 0,4 / 0,6 мс |
| HTTP p50 / p95 | 2,9 / 20,4 мс | 2,1 / 5 мс |
| event-loop lag p99 / max | 4100 / 4100 мс | 13 / 21 мс |
| ответ бота p50 / p95 | 4119 / 4131 мс | 1971 / 2289 мс |
| CPU процесса | 104 % | 183 % |
| RSS max | 217 МБ | 531 МБ |
| макс. очередь пула | — | 2 |
| бюджет | **превышен** | **соблюдён** |

Как читать результаты:

- В режиме sync WS/HTTP p95 выглядят небольшими по выборке, но lag
  достигает 4 с. Зонды, попавшие на блокировку, ждали до 4 с, а в периоды
  поиска зондов просто меньше: пока зонд ждёт, следующий не отправляется.
  Поэтому главная метрика здесь — event-loop lag.
- В режиме pool CPU и память выше: два потока считают параллельно, у каждого
  свой V8-heap и копия движка. Это осознанная цена.

## Границы измерений

- Клиенты работают в том же процессе, что и сервер. Это сделано намеренно:
  блокировка event loop видна клиентам. Но клиенты сами потребляют часть CPU
  и лишь косвенно учитываются в lag.
- Сеть — loopback, реальной сетевой задержки и потерь нет.
- Абсолютные числа зависят от машины (здесь 2 vCPU). Режимы сравнивать
  только между собой на одной машине.
- Лимит поиска (`timeLimit`) не даёт жёсткого real-time. При N strong-комнатах
  больше `size` время ответа бота растёт из-за очереди, а при переполнении
  очереди срабатывает повтор или запасной ход.
- Пул изолирует CPU от основного потока, но не от ядер машины. Если потоков
  больше, чем свободных ядер, они конкурируют с основным потоком за CPU.

## Тесты

- `test/botpool.js`:
  - реальный поиск в worker даёт легальный ход для авторитетного матча;
  - соблюдается предел параллелизма;
  - переполнение очереди даёт `queue-full`;
  - отмена работает и из очереди, и для идущего расчёта;
  - зависший поток прерывается по таймауту и заменяется новым;
  - падение потока отклоняет только его запрос;
  - `close()` не оставляет потоков.
- `test/bot-races.js` (сервер, поиск замедлен):
  - undo во время поиска: нет хода устаревшим ответом, затем ровно один ход;
  - `end` во время поиска: нет хода после gameOver;
  - реванш: ровно один ход в новой партии;
  - 4 комнаты одновременно: не больше `size` потоков;
  - `server.close()` не оставляет потоков;
  - зависший worker: таймауты, затем запасной ход без повреждения партии;
  - процесс завершается сам.
- Оба теста входят в `npm test` и `npm run test:botpool`.
