# Аудит арбитра — issue #77

Ветка: `openai-gpt-6-1-sol-issue-77`.

## Причины и изменения

1. **Несопоставимые оценки.** `trace.candidates[].score` общего alpha-beta
   поиска содержит не только точные значения, но и границы для отсечённых
   кандидатов. Сравнение такой границы спасения с максимумом корневых оценок
   не является корректным сравнением ходов. Теперь спасение и основной ход
   оцениваются одинаковой `evaluateStatic` после перехода, с точки зрения
   одного игрока — бота, с одинаковыми весами. Это консервативный статический
   фильтр, не обещание равенства тактической силы двух ходов.
2. **`no-solver` принимал тревогу за потерю.** Раньше каждая группа с `cost <= 2`
   считалась потерянной без вызова решателя: защитный ход рядом с ней мог
   запрещаться `avoid-lost`. Теперь без решателя ход поиска сохраняется.
   Прерванный решатель возвращает unknown (`incomplete`, `loss:null`), а не
   потерю или спасение. Ограничение ущерба допускается только после
   завершённого локального поиска, сообщившего потерю всей группы.
   Это всё ещё вывод *ограниченного* поиска (регион, кандидаты, горизонт),
   а не математическое доказательство неизбежной потери на всём поле.
3. **Неполный контроль времени.** Дедлайн раньше проверялся лишь раз в
   128 узлов основного локального поиска; генерация ходов, `verify`,
   `forkCheck` и вложенный `netThreat` могли работать после него.
   Теперь все фазы делят дедлайн и бюджет работы, проверяемые перед
   переходами. Одна неделимая операция перехода может немного выйти за
   дедлайн. При `opts.nodeLimit > 0` дополнительный бюджет по умолчанию
   ограничен 1500 мс (`alarmTimeLimitNodes`), также действует
   `min(alarmTimeLimit,maxAlarmTimeLimit)`.
4. **Основные узлы не расходуются локальным поиском.** Основной поиск вызывается
   первым с исходным `nodeLimit`, локальный решатель имеет отдельный бюджет.
   Лимит решателя теперь учитывает также генерацию/проверку переходов, поэтому
   его численное значение не эквивалентно прежнему лимиту рекурсивных узлов.
5. **Наблюдаемость.** В каждой партии `paired-match` для стороны с монитором
   сохраняется `games[].cand.arbiter` (или `base.arbiter`): `alarms`,
   `overridden`, `timeouts`, `decisions={base,rescue,limit}`, массивы `localMs`
   и `budgetMs`. В статистике `avoid-lost` отображается как `limit`.
   `rescue` может совпадать с основным ходом, поэтому число решений rescue
   не равно числу фактических подмен.

## Проверка на тех же 10 парах S8

Команды (Node 18+, из корня репозитория):

```sh
node tools/bench/s8-ablation.js --config full --from 0 --to 1 --out-dir out/s8-77
# Остальные шарды: [1,3), [3,5), [5,6), [6,7), [7,8), [8,10)
node tools/bench/s8-ablation.js --config full --from 1 --to 3 --no-tactics --out-dir out/s8-77
node tools/bench/s8-ablation.js --table --out-dir out/s8-77
npm test
```

Все семь JSON-шардов `out/s8-77/full.*.json` сохранены в ветке.
Использованы исходные 3000 узлов, дебюты dev/regression, правила S8,
смена сторон; ни одна партия не обрезана. Это новый прогон нашей ветки,
а не продолжение четырёх пар из комментария другой ветки в issue.

| Метрика | S8 до исправления | После исправления |
|---|---:|---:|
| Пар / партий | 10 / 20 | 10 / 20 |
| Доля очков full | 0.075 | 0.55 |
| ci95 по парам | [0, 0.175] | [0.35, 0.75] |
| p95 хода кандидата | 27.6 с | 1.964 с |
| Узлы p95 кандидата | — | 3000 |
| Средняя разность очков | — | -0.8 |

Новый результат: 11 побед, 9 поражений; улучшение силы относительно базы
**не доказано**. Нижняя граница 0.35 не больше 0.5, поэтому по ступенчатому
протоколу S8 подтверждение на 20 парах не запускается и монитор по умолчанию
не включается. Сравнение со старым прогоном диагностическое: для оценки
статистической значимости изменения относительно старого бота отдельный
парный эксперимент не выполнялся.

В 20 партиях: 772 хода кандидата, 425 тревог (55.1%), 27 реальных
подмен (3.5%), решения `base=697`, `rescue=75`, `limit=0`,
206 прерываний локального решателя. Максимальное наблюдавшееся превышение
`localMs - budgetMs` — 1.6 мс; основной поиск не входит в этот локальный
бюджет. Узлы основного поиска p95 — 3000 с обеих сторон.
S3: спасения 0/2, как у базы; тактический прирост также не показан.

Полный новый матч `no-solver` не выполнялся: режим проверен тестами на
сохранение основного хода, отсутствие вызова решателя и отсутствие подмен
при тревоге. По коду он теперь эквивалентен поиску с теми же флагами safety2
плюс диагностика монитора, а не прежнему запрету защитных ходов.

## Автотесты и ограничения

`npm test` успешно выполнен в Codespace; отдельно прошли `test/arbiter.js`,
`test/local-solver.js`, `test/paired-match.js`, `test/s8-ablation.js`.
Добавлены проверки игнорирования искусственных root bounds при сравнении
спасения, поведения no-solver/unknown, отдельного основного nodeLimit,
жёсткого малого бюджета решателя и структуры статистики по партиям.

Ограничение ущерба всё ещё ранжирует доступные корневые кандидаты по
историческим score поиска: это не исправляет все возможные ошибки их
ранжирования. В новом full-прогоне эта ветка не выбиралась (`limit=0`).
Частые тревоги и отсутствие доказанного прироста остаются основанием
сохранять monitor:false по умолчанию.
