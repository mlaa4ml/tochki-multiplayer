# Версия без игрового сервера: проект решения

Предложение для issue #1, **не уже реализованный offline-клиент**.
Цель — играть человеку с ботом и наблюдать бот–бот, меняя правила и
сравнивая алгоритмы без аккаунта, WebSocket, SQLite и запущенного `server.js`.

## Что можно использовать сейчас

`gameEngine.js` уже не зависит от сети и DOM. В Node он экспортирует
CommonJS API, а обычный браузерный `<script>` создаёт `TochkiEngine`.
`createMatch(options)` хранит независимую партию, `applyMove` проверяет и
применяет ход, `getSnapshot` отдаёт состояние для рисования.
`botMove(difficulty, weights)` выбирает ход за **текущего** игрока, а не
обязательно за место 2. Поэтому для бот–бот не нужен второй экземпляр
движка и не нужно менять константу `BOT_PLAYER`.

Но существующий `public/client.html` — сетевой клиент: он сразу открывает
WebSocket, отправляет команды серверу и рисует полученные snapshots.
Просто открыть этот HTML с диска недостаточно. Существующий
`tools/train-bot.js` работает без игрового сервера, но импортирует SQLite,
записывает веса и не даёт визуального наблюдения; это не offline-UI.

## Рекомендуемая архитектура

```text
                          ┌─ RemoteSession ─ WebSocket ─ сервер
Canvas renderer + UI ─────┤
                          └─ LocalSession ─ createMatch
                                             │ snapshot
                                             ▼
                                    Bot Worker ─ chooseMove
                                             │ координаты
                                             ▼
                                    LocalSession.applyMove
```

- Вынести отрисовку из `public/client.html` в компонент, принимающий
  snapshot и подписи игроков. Он не должен открывать сеть или менять
  правила.
- Сделать отдельную точку входа `offline/index.html`, без сетевого лобби,
  авторизации и автоматических HTTP-запросов.
- `LocalSession` — единственный владелец матча. Интерфейс адаптера:
  `newGame(options)`, `move(x,y)`, `snapshot()`, `undo()`, `end()`,
  `subscribe(listener)`, `dispose()`. Сетевой адаптер подключить позднее:
  не обязательно сразу переписывать весь работающий мультиплеер.
- Выбор контроллера **для каждого места**: человек / normal / strong /
  экспериментальный бот и свой набор весов. Выбор первого игрока —
  отдельная настройка, не перестановка идентичностей ботов.
- После каждого успешного хода читать `snapshot.current`, а не чередовать
  игроков вручную: дополнительный ход при захвате уже поддерживается
  матчем. Проверять `gameOver` перед планированием любого нового хода.
- Вычисление бота вынести в Web Worker. Основной поток передаёт snapshot,
  параметры и `{gameId, revision, requestId}`; worker возвращает ход и
  диагностику. При получении результата сверять идентификаторы и вновь
  проверять ход через `applyMove`. Сам worker не является владельцем
  партии и не должен отправлять в UI «авторитетную» доску.
- При новой партии, undo, смене режима или остановке отменять вычисление
  (`worker.terminate()` для синхронного поиска) и увеличивать revision.
  Иначе старый результат может попасть в новую позицию.

Текущий `chooseMove` не принимает полные правила матча: до исправления
этого расхождения offline-версия повторит ограничения нынешнего бота,
а не устранит их сама. См. [анализ бота](BOT_ANALYSIS.md).

## Два значения «без сервера»

### Основной вариант: статическое приложение

Папка с HTML/JS/CSS, доступная через любой статический хостинг (например,
GitHub Pages) или локальную раздачу файлов. Игрового backend нет; HTTP
используется только для загрузки ресурсов. Все партии и поиск локальны.

Один канонический `gameEngine.js` должен попадать в статическую сборку
автоматически, а не поддерживаться второй ручной копией. Статическая
сборка включает движок, worker и UI, не включает `db.js`, `auth.js`,
`server.js` или зависимости `ws`/`better-sqlite3`.

На следующем этапе — PWA с service worker, кешированием всех ресурсов
и явной версией кеша. После первой успешной загрузки приложение должно
работать с отключённой сетью. Для service worker требуется HTTPS
(либо localhost); это не то же самое, что открытие через `file://`.

### Дополнительный вариант: совсем без HTTP, двойной клик по HTML

Если нужен именно `file://`, собирать отдельный автономный HTML с
встроенными стилями, UI и движком; избегать `fetch`, ES module imports,
CDN и загрузки worker через внешний URL. Worker можно создавать из Blob
со встроенным кодом движка, но совместимость и CSP нужно отдельно
проверять в целевых браузерах. При недоступности worker — явное сообщение
или ограниченный синхронный режим normal, не молчаливое зависание UI.

Этот вариант сложнее в поддержке, поэтому сначала согласовать с автором:
достаточно ли статической страницы/PWA, или обязателен запуск файлом.
PWA и локальный HTML — альтернативные артефакты одной кодовой базы,
а не два независимых движка.

## Минимальный интерфейс лаборатории

1. Настройки: поле, порог очков/заполнения, дополнительный ход, первый
   игрок, возможность отмены, контроллер и веса каждого места.
2. Человек–бот: клики только в ход человека; индикатор вычисления;
   restart/end/undo без применения запоздалого ответа бота.
3. Бот–бот: запуск, пауза, ровно один шаг, скорость показа, счёт,
   текущий игрок, число ходов, последний ход каждого игрока.
   Пауза не должна незаметно разрешать ещё один ход после возврата worker.
4. Просмотр и экспорт реплея: настройки правил, версия движка/бота,
   начальный seed/лимит узлов, события ходов/отмен/завершения.
   Не сохранять только итоговую доску.
5. Для исследования: кандидаты, оценки, достигнутая глубина, число узлов,
   причины окончания поиска и выбранный ход. Диагностику придётся добавить
   к API поиска: нынешний `botMove` этих данных не возвращает.

Импорт реплея должен проверять версию, размеры, числовые пределы,
последовательность событий и легальность всех ходов; ошибка не должна
оставлять наполовину изменённую текущую партию. Отмена и ручное окончание
должны быть событиями, а не потерянной информацией. LocalStorage — только
настройки/небольшая автосохранённая партия; большие коллекции — IndexedDB
и экспорт JSON. Отказ хранилища не должен мешать игре.

## Headless-стенд для сравнения ботов

В дополнение к UI выделить чистый runner без импорта БД:
`createMatch → snapshot → chooseMove → applyMove → JSONL события`.
Один и тот же runner/контракт должен использоваться в браузере и CLI.
Проверять ошибки каждого хода, не считать невалидный ход ничьей.
Ограничение времени/ходов помечать как truncation, не как обычное
завершение по правилам. Конфигурация и версия алгоритма входят в отчёт.

Первые smoke-прогоны — маленькое поле и короткая партия; полноценные
парные турниры — отдельная длительная задача. Seed сам по себе не делает
нынешний поиск воспроизводимым: нужен детерминированный лимит узлов.

## Этапы и проверяемая готовность

| Этап | Результат | Критерий приёмки |
| --- | --- | --- |
| O1 | Чистый renderer и LocalSession | Одинаковая последовательность ходов даёт одинаковые snapshots в Node и браузере; нет копии правил |
| O2 | Offline человек–бот | Партия до конца без WS/API/SQLite; оба первых игрока, оба уровня, undo и дополнительный ход проверены |
| O3 | Worker и бот–бот | UI реагирует во время strong; шаг ровно один; pause/restart/undo не применяют устаревший ответ; серия не ходит после gameOver |
| O4 | Реплеи и headless runner | Экспорт → импорт воспроизводит доску, очередь, счёт и конец; повреждённый реплей отклоняется; правила версионированы |
| O5 | Статическая сборка и при необходимости PWA/file-артефакт | Нет внешних ресурсов; после установки PWA игра работает offline; отдельный file-тест, если выбран этот режим |

Браузерные тесты: Chromium и Firefox как минимум; мобильные размеры и
touch; режим отключённой сети; отсутствие незапланированных запросов;
ошибка worker и отказ storage. Интеграционные тесты LocalSession —
с управляемым fake worker для проверки гонок. Движок и поиск —
с отдельными тактическими тестами из плана усиления бота.

## Предлагаемый порядок относительно усиления бота

Сначала зафиксировать правила и воспроизводимые позиции; затем O1–O3,
чтобы автор мог наблюдать проблемные решения. Параллельно исправлять
семантику переходов в поиске. После O4 проводить измеримые эксперименты
с глобальными признаками и весами. Упаковка PWA и косметика O5 не должны
откладывать исправление правил или создание контрольного набора.
