# Headless runner и парный benchmark ботов (A07, issue #12)

Это **инфраструктура измерения**. Она не заявляет, что бот стал сильнее.
`tools/train-bot.js` подбирает веса. Benchmark — независимый контроль силы. Он устроен так:

- не импортирует `db.js` и `gamelog.js`;
- не читает дебюты из БД;
- **никогда не сохраняет и не публикует веса**.

## Состав

| Файл | Назначение |
|---|---|
| `tools/bench/runner.js` | Чистый runner: `createMatch → getSnapshot → chooseMove → applyMove → JSONL`. Модуль UMD с общим контрактом для браузера и CLI: в браузере доступен как `TochkiBenchRunner`, движок передаётся аргументом. |
| `tools/bench/benchmark.js` | Генератор корпуса, строгая проверка корпуса, парный турнир, bootstrap, машинный отчёт. |
| `tools/bench/corpus/openings.v1.json` | Версионированный корпус: дебюты `train/validation/test` для полей small/medium и тактика `capture-in-1`. Сгенерирован с seed 20240612. |
| `tools/bench/baseline/weights.v1.json` | Замороженный baseline (копия `BOT_WEIGHTS` на момент A07) и пул соперников. |
| `tools/bench/reports/sample.json` | Сохранённый пробный отчёт. |
| `test/bench.js` | Быстрый smoke-тест на малом поле (~1 с). Входит в `npm test`. |

## Контракт runner

`playGame(Engine, { rules, players: {1: chooseMove, 2: chooseMove}, prefix, maxMoves, maxMs, meta, clock })`

- `chooseMove(snapshot) -> { move: {x,y} | null, trace }`. Стандартная реализация — `makeSearchPlayer(Engine, { difficulty, nodeLimit, weights })`. Она вызывает `Engine.searchMove` с детерминированным лимитом узлов, таймер выключен.
- Каждый ход проверяется через `match.applyMove`. Нелегальный ход бота или нелегальный ход префикса дебюта вызывает **`InvalidMoveError`**. Такая партия не засчитывается ничьей, а попадает в `report.errors`.
- Способ завершения партии записывается в поле `end`:
  - `finished` — штатный конец по правилам;
  - `no-move` — нет легальных ходов;
  - `truncated-moves` — партия обрезана по лимиту ходов;
  - `truncated-time` — партия обрезана по лимиту времени.

  Флаг `truncated` выставляется только для двух последних случаев. Доля обрезанных партий выводится в отчёте отдельно.
- Формат JSONL — записи по порядку:
  - `header`: версии runner/движка/бота/весов, полные правила с `sizeKey`, `meta`;
  - `prefix` — ходы дебюта;
  - `move` — ход с полями `seat, x, y, ms, nodes, depth, stop`;
  - `result`.

  `replayLines(Engine, lines)` заново проигрывает запись и сверяет счёт.

## Корпус и сплиты

- `train` — разрешено использовать при подборе весов. **Benchmark отказывается измерять `train`.**
- `validation` — быстрые проверки и отладка инструмента.
- `test` — независимая выборка для решения о принятии весов.
  - Её нельзя использовать в подборе весов: ни в `train-bot.js`, ни при ручном переборе.
  - Если по результатам `test` веса меняли и мерили снова, выборка «сожжена». Нужна новая версия корпуса.
- Корпус не редактируется. Новая версия — это новый файл `openings.vN.json` с другим seed: `--gen-corpus <path> --seed N`.
- При каждом запуске `validateCorpus` строго проверяет корпус:
  - каждый префикс целиком проигрывается легальными ходами и не заканчивает партию;
  - id уникальны.

  Ошибка в любом префиксе — это отказ запуска, а не молчаливая обрезка, как было в `train-bot.js`.
- Правила в корпусе (`rulesets`):
  - `fill30` — заполнение 30%;
  - `fill30-extra` — заполнение 30% с дополнительным ходом за захват;
  - `score3-fill45` — до 3 очков или 45% заполнения.
- Тактика `capture-in-1`: позиции, где у ходящего есть немедленный захват. Ожидаемые ходы — все клетки с приростом очков, это проверено реальным `applyMove`. В корпусе v1 таких позиций мало: 4 на small и 2 на medium. Метрика «пропуски тактики» пока грубая.

## Схема турнира

- **Пара** — один дебют, сыгранный дважды: кандидат играет и за seat 1, и за seat 2. Оба бота работают с одной сложностью и одинаковым `nodeLimit`, то есть с равным бюджетом узлов.
- Конфигурации — декартово произведение полей (`--sizes`), сложностей (`--difficulties normal,strong`) и соперников: baseline плюс пул.
- Независимые прогоны (`--runs`): у каждого свой seed `seed + run·7919` и свой порядок дебютов.
  - При лимите узлов результат детерминирован, а порядок на исход партий не влияет.
  - Поэтому прогоны проверяют повторяемость и устойчивость инструмента. Новой информации о силе бота они не добавляют.
  - Для реально независимой выборки нужно больше дебютов или новая версия корпуса.

## Метрики отчёта (`format: tochki-bench-report`)

На каждую конфигурацию:
- W/D/L;
- `truncationRate`;
- `scoreDiffMean` — средняя разница очков кандидата;
- `score` — доля очков кандидата;
- `ci95` — bootstrap по парам дебютов;
- `nodesPerMove`, `completedDepth`;
- `moveMs.p50/p95`;
- `tactics` — пропуски тактики, считаются только против baseline;
- `runs` — seed каждого прогона.

На верхнем уровне:
- `code` — commit, `ENGINE_VERSION`, `BOT_VERSION`, `WEIGHTS_VERSION`;
- `corpus` — версия, seed, сплит;
- `params` — включая параметры сложностей;
- `candidate` и `pool` с весами;
- `errors`;
- `vsBaseline` — сводный интервал по всем парам против baseline;
- `acceptance`.

## Критерий принятия усиления (зафиксирован ДО экспериментов)

Кандидат считается сильнее baseline, только если выполнены оба условия:

1. Нижняя граница 95% интервала (bootstrap по парам дебютов, сплит `test`, все конфигурации против замороженного baseline) **строго больше 0.5**.
2. **Ноль ошибок корректности**: `report.errors` пуст, то есть нет невалидных ходов и ошибок префиксов. Smoke-тест replay в `npm test` проходит.

Отчёт выставляет `acceptance.accepted`, но **ничего не публикует**. Решение о переносе весов в `BOT_WEIGHTS` или в БД человек принимает отдельным коммитом. Критерий нельзя ослаблять задним числом, глядя на результаты.

## Команды

```bash
npm run test:bench        # smoke, ~1 с (также входит в npm test)
npm run bench             # пробный отчёт: validation, small, normal, 2 прогона × 3 пары, node-limit 300 (~30 с)
npm run bench:full        # полный турнир: test, small+medium, normal+strong, 3 прогона, node-limit 4000
node tools/bench/benchmark.js --full --candidate my-weights.json --out tools/bench/reports/cand.json
node tools/bench/benchmark.js --gen-corpus tools/bench/corpus/openings.v2.json --seed 777   # новая версия корпуса
```

Параметры: `--split`, `--sizes`, `--difficulties`, `--node-limit`, `--runs`, `--seed`, `--max-moves`, `--max-ms`, `--bootstrap`, `--max-pairs`, `--candidate` (JSON с `weights`), `--baseline`, `--corpus`, `--jsonl`.

Оценка длительности полного турнира:
- 12 дебютов × 2 поля × 2 сложности × 3 соперника × 3 прогона × 2 цвета = 864 партии;
- узлов на ход примерно в 13 раз больше, чем в пробном отчёте;
- поле medium длиннее small.

Итого — **порядка нескольких часов**. Это задача для ручного или ночного запуска, не для CI.

## Пробный отчёт (`tools/bench/reports/sample.json`)

Параметры: кандидат = веса движка (совпадают с baseline), validation, small, normal, node-limit 300, 2 прогона × 3 пары.

| Соперник | W/D/L | Score | 95% CI |
|---|---|---|---|
| baseline | 2/8/2 | 0.5 | [0.5, 0.5] |
| no-liberty | 6/4/2 | 0.67 | [0.42, 0.92] |
| territory-heavy | 2/8/2 | 0.5 | [0.5, 0.5] |

Прочие показатели:
- обрезанных партий: 0;
- ошибок: 0;
- время хода: p50 ≈ 27 мс, p95 ≈ 38 мс;
- пропусков тактики: 0 из 4;
- `accepted=false` — это ожидаемо для кандидата, который совпадает с baseline.

## Статистические ограничения малой выборки

- **Самоигра одинаковых весов даёт вырожденный интервал [0.5, 0.5].** Две партии пары зеркальны по детерминированному алгоритму, поэтому каждая пара даёт ровно 0.5. Это проверка корректности парной схемы, а не оценка точности.
- В пробном отчёте уникальных пар всего 3: два прогона повторяют те же дебюты.
  - Bootstrap по 6 «парам» занижает ширину интервала, потому что повторы не независимы.
  - Даже против `no-liberty` интервал [0.42, 0.92] включает 0.5.
  - Выводы о силе по пробному отчёту делать нельзя.
- Bootstrap перцентильный, без коррекции смещения. Он плохо ведёт себя:
  - при числе пар меньше ~30;
  - при score около 0 или 1;
  - при многих одинаковых значениях пар — дискретность 0, 0.5, 1.
- Сводный `vsBaseline` объединяет поля и сложности. Сильный эффект в одной конфигурации может скрыть регрессию в другой, поэтому смотрите и `configs[]`.
- При проверке нескольких кандидатов на одной выборке `test` растёт вероятность ложного принятия. Это множественные сравнения. Проверяйте одного заранее выбранного кандидата или используйте новый корпус.
- Ограничения корпуса v1:
  - дебюты — короткие случайные легальные префиксы (4–6 ходов), а не партии людей;
  - тактических позиций мало.

  Для реального контроля силы нужен корпус v2 с бо́льшим числом дебютов (≥ 50 пар на конфигурацию) и тактикой из реальных партий.
- Лимит узлов делает результат повторяемым, но не равен по силе игровому таймеру `DIFFICULTY.*.timeLimit`. Benchmark меряет алгоритм при равном бюджете узлов, а не силу бота в реальном времени.
