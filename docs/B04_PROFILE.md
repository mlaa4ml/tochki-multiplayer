# B04 — профиль и ускорение поиска бота (issue #27)

## Как снимался профиль

Команда:

```
node --expose-gc tools/bench/profile-search.js --repeat 3 --nodes 4000 --out <report.json>
```

Условия замера:

- Корпус — `tools/bench/corpus/strategic.v1.json`, корпус A07: 24 позиции, `prefix` и `rules` у каждой свои.
- Сложность — `normal`, веса — `BOT_WEIGHTS`.
- Лимит узлов — `nodeLimit = 4000`, детерминированный. Таймер выключен.
- Каждая позиция прогоняется 3 раза.
- Среда — Node v24.21.0 в GitHub Codespaces.

Что считает скрипт:

- **Время хода** — p50 и p95 по всем прогонам.
- **Число узлов** — `totalNodes`, сумма `trace.nodes`.
- **Память** — `maxHeapDeltaMB`, максимальный прирост `heapUsed` за один поиск после `gc()`.
- **Сигнатура** — `signature`: по каждой позиции записываются `id`, ход, `nodes` и `completedDepth`.

Если повторные прогоны одной позиции дают разный результат, скрипт падает. Так проверяется детерминизм.

CPU-профиль снят до изменений командой `node --cpu-prof tools/bench/profile-search.js --repeat 1 --nodes 4000`. Доля по self time:

| функция | доля |
|---|---|
| `runCaptures` | 33.4% |
| сборщик мусора | 15.4% |
| `captureSuicideRegion` | 6.6% |
| `computeGroupLiberties` | 5.6% |
| `strategicCandidates` | 3.2% |
| `legalCandidates` | 3.0% |
| `cloneState` | 1.5% |
| `applyTransition` | 0.5% |

Вывод из профиля: копирование узлов **не является bottleneck** (`cloneState` + `applyTransition` дают около 2%). Поэтому make/unmake вместо копирования, по условию issue, **не делался**.

Основная стоимость — заливки в `runCaptures` и `captureSuicideRegion`, а также GC. GC вызывают аллокации пар `[x,y]` и массива направлений на каждую клетку.

| 1. `runCaptures`: заливка на `Uint8Array`/`Int32Array` | `reports/b04-profile-step1-runcaptures.json` | 2296 | 7.35 | 90.01 | 7.56 | да | оставлен |
| 2. `captureSuicideRegion`: то же | `reports/b04-profile-step2-suicide.json` | 2296 | 4.59 | 89.13 | 8.07 | да | оставлен |

Итог (шаги 1–3, код в ветке): p50 ускорился примерно в 5 раз, p95 — примерно в 3.3 раза, пиковый прирост heap снизился с 30.8 до ~13.5–15.8 МБ. Число узлов, ходы и глубина на всех 24 позициях совпадают с исходными при одинаковом лимите узлов. Контрольный прогон после отката шага 4: 2296 узлов, p50 5.65 мс, p95 88.72 мс, heap 15.81 МБ, сигнатура совпадает.

### Шаги 1–2: заливки на плоских массивах

Порядок обхода сохранён: в `runCaptures` соседи обходятся в порядке +x, −x, +y, −y, в `captureSuicideRegion` — в порядке `DIRS4`; стек в обоих случаях LIFO. Поэтому итоговое состояние доски и порядок `gained`/`out` идентичны прежним.

### Шаг 3: таблица транспозиций

Таблица работает внутри одного `searchMove` и хранится в `sc.evalTT`.

Ключ включает:

- очередь хода (`current`);
- правила: `targetScore`, `targetFillPercent`, `extraTurnOnCapture`;
- `stonesPlacedTotal`;
- все три слоя доски.

`forPlayer` и `weights` в пределах одного поиска постоянны, поэтому в ключ не входят. Таблица кеширует только `evaluateStatic`. Эта функция детерминирована, так что дерево поиска и счётчик узлов не меняются.

Размер таблицы ограничен: не более 200 000 записей.

Результат шага: выигрыш по времени в пределах шума (p50 −5%), а память выросла примерно на 5 МБ. Статическая оценка в этом профиле не горячая точка. Шаг оставлен, потому что он корректен и ограничен по памяти, но его стоит пересмотреть при более глубоком поиске. Отсечения по TT-границам alpha/beta намеренно не вводились: они меняют число узлов и ходы при том же лимите, то есть нарушают критерий детерминизма относительно эталона.

### Шаг 4: кеш карт (измерен и откатан)

Попытка: кешировать результат `computeGroupLiberties` на узел поиска (WeakMap по объекту узла, сброс в `applyTransitionInPlace`) и использовать его в `evaluateStatic` и `strategicCandidates`, где карта групп одной позиции считается по несколько раз.

Замер (тот же корпус и команда): узлы 2296, сигнатура совпала, тесты A01/transition/search/undo зелёные, но:

- p50 11.05 мс, p95 264.85 мс в первом прогоне; в парном прогоне в одной среде — p50 6.84 / p95 95.38 мс против 5.35 / 93.12 мс без кеша (шаг 3), то есть ускорения нет;
- пиковый прирост heap вырос с ~15.8 до ~61.6 МБ: кеш удерживает массивы групп с `Set` свобод для каждого узла, а повторных обращений к одному узлу мало.

Вывод: на этом профиле кеш карт вреден по памяти и не даёт выигрыша по времени, поэтому изменение **откатано** (в `gameEngine.js` его нет), отчёт замера сохранён для истории. Возвращаться к нему имеет смысл только вместе с более дешёвым представлением групп или при большем `nodeLimit`, если профиль покажет иное.

## Корректность

После каждого шага (включая откат шага 4) прогонялись тесты, все зелёные:

- `test/rules.js` — контракт правил A01: 687 проверок, 11 эталонов, Node == browser;
- `test/transition.js` — 122 850 проверок;
- `test/search.js` — бюджет, прерывание, trace, Worker;
- `test/undo.js`.

Веса оценки и алгоритм поиска не менялись: это задачи B05 и B06.
