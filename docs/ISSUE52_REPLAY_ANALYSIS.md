# Issue #52: доработка по человеческим реплеям

## Что проверено

Основание — два JSON-вложения автора issue #52. Их копии находятся в
`tools/bench/corpus/human/issue52-replays01.json` и `issue52-replays02.json`.
Это шесть проигрышей strong: четыре small и два medium; старт cross,
первый игрок — бот (seat 2), заполнение 64 %, без дополнительного хода.
Финальные счета человек:бот: 12:0, 16:0, 24:0, 27:0, 36:0, 35:0.
Это выборка проигрышей, а не оценка частоты побед на всех партиях.

`tools/bench/analyze-human-replays.js` воспроизводит события движком,
проверяет допустимость реплея и получает позиции до ходов. Только для
анализа из копии удаляется legacy-поле `decision`, не соответствующее
текущему контракту replay.js. Исходные файлы не изменяются.

Метрика потери: увеличение счёта противника после нашего хода и его
лучшего немедленного легального ответа. Для завершённой партии и
дополнительного своего хода ответ противника не выдумывается.
Перебор всех легальных наших ходов даёт минимум этой **локальной**
метрики, а не оптимальный ход всей партии.

Обнаружено 35 позиций с ненулевой потенциальной потерей после записанного
хода. Это не «35 зевков»: многие потери уже неизбежны; потенциальный ответ
также не обязан совпадать с реально сыгранным человеком.

## Причина и изменение

В `gameEngine.js` существовал полный тактический генератор, но по умолчанию
внутри дерева полный скан ограничивался корнем (`tacticalPly:0`).
На первом ответе противника локальная генерация/ограниченная ширина могли
не дать поиску увидеть немедленный захват. Глубина сама по себе не помогает,
если нужный ответ не попал в кандидаты.

Теперь значение по умолчанию — `tacticalPly:1`: полный тактический скан
работает также на первом ответе. Это переиспользует существующую тактику,
ограничения кандидатов и механизм остановки поиска, не добавляет отдельный
неограниченный предварительный фильтр. Это не полный перебор всего дерева:
сохраняются tacticalCap, beam, ограничение глубины и бюджета.
Для сравнения/отката передайте в конфигурации сложности `tacticalPly:0`.
Правила игры, веса и формат реплеев не меняются.

## Измерения и границы результата

`tools/bench/reports/issue52-replies.json` содержит сравнение всех 35 позиций
при **5000 узлов**, strong, с выключенным обычным таймером:

- в 11 позициях локальная потеря уменьшилась;
- в 23 не изменилась;
- в 1 выросла: `issue52-replays02.json#3`, eventIndex 104, с 3 до 4.
  Расширенный поиск при ограниченном бюджете не гарантирует монотонности
  качества; эта регрессия явно сохранена в отчёте, а не исключена из выборки.
- В том же реплее на событиях 66, 68, 70 потери стали 0 вместо 8, 1, 1.
  `test/human-replays.js` строго проверяет эти три случая, допустимость хода,
  детерминизм и отсутствие изменения исходного снимка.

eventIndex и координаты — с нуля. Отчёт содержит также глубину, узлы,
причину остановки и время. 5000 узлов не эквивалентны серверному таймеру:
отдельные позиции занимали более двух секунд. Нельзя обещать те же ходы
при обычном лимите strong в 2000 мс.

`issue52-smoke.js` сыграл две полные партии со сменой сторон на small/cross,
64 %, 300 узлов, tacticalPly 1 против 0: победа кандидата 1:0 и ничья 0:0.
Нелегальных ходов и усечённых партий не было. Это только smoke-проверка,
**не доказательство общего усиления и не независимый статистический gate**.
Шесть человеческих проигрышей использовались при разработке, поэтому они
тоже не являются независимым test-набором.

В Codespace прошли:
- `node test/human-replays.js`;
- `node test/rules.js` — 687 проверок, Node/browser;
- `node test/transition.js` — 122850 проверок;
- `node test/candidates.js`;
- `node test/search.js` — бюджет, остановка, детерминизм, Worker; наблюдаемое
  превышение таймера на его маленькой выборке 0–1 мс.

Это ограниченный набор проверок, не весь npm test и не полный benchmark.

## Воспроизведение

Node 24, корень репозитория:

```sh
node test/human-replays.js
node tools/bench/analyze-human-replays.js > /tmp/issue52-analysis.json
node tools/bench/compare-human-replays.js > /tmp/issue52-replies.json
node tools/bench/issue52-smoke.js > /tmp/issue52-smoke.json
node test/rules.js && node test/transition.js && node test/candidates.js && node test/search.js
```

Сравнение на Codespace заняло около 80 секунд, smoke — около 14 секунд;
время зависит от машины. Значения elapsedMs не детерминированы.

## Пошаговый план следующих улучшений

1. **Наблюдение реального режима.** Сохранять trace вместе с версией бота,
   весами, правилами и временем. Для каждого плохого хода различать:
   кандидат не создан, отрезан шириной, не исследован до таймера или неверно
   оценён. Сравнить normal/strong на реальных таймерах и крупных полях.
2. **Расширить регрессии.** Сохранять позиции за несколько ходов до первого
   неизбежного захвата, включая event 104 как известный отрицательный пример.
   Проверять риск, свои захваты и итог партии, а не только одну метрику.
3. **Библиотека тактики.** Добавлять по одному: захват в два хода, вилка,
   анти-вилка, защитная связка, отрезание от края. Для каждого — положительные
   позиции, контрпримеры, отражения/смена цветов, порог завершения и extra turn.
   Сначала обязательные кандидаты, затем поиск их опровержений в общем бюджете.
   «Без ошибок» можно утверждать только для проверенного конечного корпуса.
4. **Оптимизация.** Профилировать полные сканы на реальных снимках, кэшировать
   только с полным ключом правил/очереди/доски. Мерить p50/p95 времени и
   завершённую глубину при равном времени, отдельно от равного числа узлов.
   Не увеличивать одновременно ширину, глубину и набор признаков.
5. **Обучение на истории.** Импортировать обезличенные реплеи с согласия
   игроков, валидировать текущими правилами, удалять дубликаты. Разбивать
   train/validation/test по целым партиям (и их симметриям), до выделения
   позиций. Записанный ход человека не считать автоматически лучшим.
   Размечать альтернативы более глубоким анализом, проверять тактическим
   оракулом; спорные примеры хранить отдельно.
6. **Подбор политики/оценки.** Сначала использовать размеченные позиции для
   регрессий и сортировки кандидатов; веса обучать на целевой сложности,
   не только на учебной. Дебютную книгу ограничивать проверенными продолжениями
   с учётом правил. Автоматического самообучения в этой доработке нет:
   инструмент диагностики создаёт данные, но не публикует веса.
7. **Независимая приёмка.** До широкого включения проверить парные партии со
   сменой цветов на неиспользованных дебютах, small/medium/large,
   normal/strong, реальных таймерах и разных правилах. Фиксировать проигрыши,
   ничьи, усечения, задержки и доверительный интервал по независимым парам.
   Мини-smoke здесь недостаточен для критерия `ci95.lo > 0.5`.
8. **Контролируемое внедрение.** Сравнить новую настройку с `tacticalPly:0`
   на пользовательских партиях; при росте задержек/ошибок откатить параметр.
   Веса выпускать отдельно после независимой проверки, не смешивая эффект
   поиска и обучения.

Уточнения к автору: повторяются ли эти ошибки на текущей серверной версии
или только offline? Допустимы ли более долгие ходы strong? Можно ли получить
новые, не использованные при разработке партии, включая победы бота, для
независимой оценки? Эти вопросы не мешают воспроизведённой локальной правке,
но нужны, чтобы не выдавать улучшение трёх позиций за решение всей игры.
