# Почему бот всё ещё играет слабо и как это исправить — план (issue #52)

Статус: **черновик, раунд 1.** Разделы, помеченные «проверить», будут
уточнены по коду и отчётам `tools/bench/reports/*`, `docs/A09_VALIDATION.md`,
`docs/B05_WEIGHTS.md`, `docs/B06_MCTS.md` в следующих раундах. Документ не
утверждает, что сила бота уже измерена или повышена.

## 1. Почему настройки по умолчанию работают плохо (факты из кода)

Настройки в `gameEngine.js`:

```
normal: radius 2, candidateCap 10, timeLimit 220 мс, maxDepth 3, branch 5/4/3
strong: radius 4, candidateCap 20, timeLimit 2000 мс, maxDepth 6, branch 8/6/5
TRAIN_DIFF: radius 3, candidateCap 16, timeLimit 700 мс, maxDepth 4
BOT_WEIGHTS = { potential: 6, cohesion: 1.2, stones: 0.15, liberty: 5 }
```

1. **Веса подобраны не для того режима, в котором играет человек.**
   `BOT_WEIGHTS` — ручная стартовая точка (так сказано в комментарии к коду);
   self-play в `tools/train-bot.js` подбирает их под `TRAIN_DIFF`, который
   не совпадает ни с normal, ни с strong. Хорошие веса для глубины 4/700 мс
   не обязаны быть хорошими для глубины 3/220 мс или 6/2000 мс.
2. **Обрезка кандидатов важнее глубины.** Корень ограничен 10/20 ходами,
   внутренние уровни — 3–8 ходами, а генератор предлагает клетки рядом
   с существующими точками (radius 2/4). Стратегически важный ход вне этой
   зоны вообще не рассматривается, и никакая глубина его не вернёт.
   При ширине 3–5 на внутренних уровнях бот фактически видит одну-две
   линии ответа соперника — отсюда «зевки» в двухходовых комбинациях.
3. **Номинальная глубина ≠ достигнутая.** maxDepth 6 у strong — верхняя
   граница; при 2000 мс и дорогой оценке реальная `completedDepth` может
   быть меньше. Это видно в `trace` (A04), но по умолчанию не показывается
   и не контролируется. *Проверить:* распределение `completedDepth` в
   `tools/bench/reports/b04-*.json` и `tools/load/reports/a10-*`.
4. **Оценка — аналогия с го.** Вес `liberty` (5) почти равен `potential` (6),
   а «свободы» в этих правилах не означают безопасность (точка у края не
   захватывается заливкой). Ошибочный сигнал с большим весом уводит поиск.
5. **Оценка не знает фазы партии и порога победы**, поэтому в конце бот
   продолжает «строить форму», вместо того чтобы добирать очки.

## 2. Как улучшить и оптимизировать игру (по приоритету)

| # | Шаг | Ожидаемый эффект | Как проверять |
|---|-----|------------------|---------------|
| 1 | Тактический набор позиций: «захват в 1/2/3 хода», «защита от захвата в 1/2 хода», «замкнуть до выхода к краю» (расширить `tools/bench/corpus/strategic.v1.json`) | Измеримая метрика «доля ошибок» вместо субъективного «плохо играет» | `tools/bench/strategic.js`: % найденных эталонных ходов отдельно для normal/strong |
| 2 | Обязательные кандидаты до обрезки: все реальные захваты, все ходы, закрывающие угрозу соперника (по `urgentMap`), ходы на разрывах контуров | Убирает класс ошибок «ход не рассматривался» | доля пропусков на п.1 → 0 для угроз в 1 ход |
| 3 | Угрозы соперника считать симметрично: перед ходом найти все клетки, где соперник захватывает следующим ходом | Бот перестаёт отдавать группы | тот же набор, раздел «защита» |
| 4 | Пересчитать веса для каждого режима отдельно (normal и strong — свои наборы, `TRAIN_DIFF` убрать или сделать равным целевому режиму) | Веса соответствуют реальному бюджету | парный benchmark `tools/bench/benchmark.js`, 95% интервал, нижняя граница > 0.5 |
| 5 | Ablation `liberty`: вес 5 → 0/2/5, заменить на признак «расстояние области до края по стенам соперника» (A09) | Убирает ложный сигнал | парный benchmark + тактический набор |
| 6 | Фазовая оценка: при близком пороге очков/заполнения вес текущего счёта растёт | Меньше проигрышей в концовке | позиции концовки в корпусе |
| 7 | Ускорение только после профиля (TT, кеш карт, make/unmake — B04) | Больше реальной глубины при том же времени | `completedDepth` p50/p95 при тех же ходах |
| 8 | Normal: давать больше ширины, а не глубины (например branchNarrow 3 → 4), если время позволяет | Меньше двухходовых зевков | p95 времени хода ≤ бюджета |

## 3. Обучение на истории партий с человеком

Нужные данные уже частично есть (A02: полные реплеи; `gamelog.js`, `replay.js`).
Пошагово:

1. **Сбор.** Из БД выгрузить реплеи «человек–бот» полностью (правила,
   первый игрок, отмены), исключить партии с отменами после ошибки бота
   или помечать их отдельно.
2. **Разметка ошибок бота.** Для каждой проигранной ботом партии прогнать
   каждую позицию анализатором с большим бюджетом (strong ×10 по узлам).
   Ход бота, после которого оценка упала больше порога, — ошибка;
   позиция + правильный ход добавляются в тактический корпус (п.1 раздела 2).
   Это главный канал «обучения»: корпус растёт из реальных проигрышей,
   и каждая новая версия бота обязана решать все ранее найденные ошибки.
3. **Дебютная книга.** Частые первые 6–10 ходов людей и их результаты →
   книга дебютов: в известной позиции бот играет проверенный ответ без поиска.
4. **Позиции для подбора весов.** Префиксы человеческих партий использовать
   как стартовые позиции для self-play (train/validation/test раздельно),
   а не только первые 6 ходов, как сейчас в `train-bot.js`.
5. **(Позже) policy-модель.** Когда наберутся тысячи партий: простая модель
   «вероятность хода человека/сильного анализатора» для сортировки кандидатов
   (не для замены поиска). *Проверить:* выводы эксперимента B06 в
   `docs/B06_MCTS.md`.

## 4. Набор «алгоритмов-приёмов», которые бот разыгрывает без ошибок

Предлагается модуль шаблонов (паттернов) с детектором и проверкой поиском:

| Приём | Детектор | Действие |
|-------|----------|----------|
| Добивание захвата | область соперника, замыкаемая 1 ходом | играть немедленно |
| Защита от захвата | соперник замыкает 1 ходом | закрыть разрыв / вывести к краю |
| Двойная угроза («вилка») | ход создаёт ≥2 независимых захвата в 1 ход | приоритетный кандидат |
| Лестница/погоня к краю | цепочка вынужденных ответов | просчитывать до конца как продление (quiescence) только по вынужденным ходам |
| Отрезание от края | группа соперника ≤ N клеток до края | ход, перекрывающий кратчайший путь |
| Защитная связка | две свои группы, соединение одним ходом | кандидат при угрозе |

Правило внедрения каждого приёма: детектор → тестовые позиции (≥10 на
приём) → кандидат обязательно попадает в поиск (а не заменяет его) →
парный benchmark против текущего бота. Приём принимается, только если не
даёт регрессий. Так бот «знает» приём и не ошибается в его розыгрыше,
но окончательное решение остаётся за поиском.

## 5. Пошаговый план

1. Метрика: тактический корпус + отчёт «% ошибок» для normal/strong.
2. Обязательные кандидаты (захват/защита в 1–2 хода) — до обрезки.
3. Детекторы приёмов из раздела 4 по одному.
4. Ablation `liberty`, признак связи с краем, фазовая оценка.
5. Отдельные веса для normal и strong, парный benchmark.
6. Разбор проигранных партий с человеком → пополнение корпуса (регулярно).
7. Дебютная книга из реплеев.
8. Профилирование и ускорение.
9. Эксперимент policy-модели для сортировки кандидатов.
