# S3. Позиции «до вилки» и тактический тест на улучшение (issue #57)

Часть дорожной карты #53 (`docs/MONITOR_ROADMAP.md`, раздел S3). Источник: п. 5.2 Плана.

## Зачем

Все 6 позиций в `test/replay-blunders.js` уже обречены: группа к этому моменту
потеряна, минимальный риск — 6–13 точек. Допуск «минимум + 1» ловит только
регрессию и не может показать улучшение. Поэтому нужны позиции на несколько
ходов раньше, где спасение ещё существует.

## Как ищутся позиции

Режим `--prefork` в `tools/bench/replay-blunders.js`:

```
node tools/bench/replay-blunders.js --prefork [файл] [--split regression] [--game <id>] \
     [--max-back 5] [--radius 2] [--min-loss 4] [--fork-cap 40] [--node-limit N]
```

По умолчанию результат пишется в `tools/bench/corpus/prefork.regression.json`.
Запись идёт слиянием по ключу «партия + ход», поэтому партии можно прогонять
по одной: на одну партию уходит 30–85 с.

1. **Взятия у бота.** Ищутся ходы соперника, которые пленили не меньше
   `--min-loss` точек (по умолчанию 4).
2. **Ход назад.** От каждого такого взятия рассматриваются ходы бота в
   обратном порядке, не дальше `--max-back` (по умолчанию 5) ходов бота.
3. **Решатель «есть ли защита».** Функция `preforkLoss` для хода бота `m`
   считает `forkLoss4` после `m` минус собственный захват ходом `m`. Это
   6 полуходов: ход бота → ответ соперника → защита бота → два хода соперника.
   Если `forkLoss4` обрывается по бюджету `--fork-cap`, решатель
   откатывается на `twoMoveThreat` (3 полухода); такие ходы помечены в наборе
   `measure: "twoMove"`.
4. **Какие ходы бота перебираются.** Клетки в радиусе `--radius` от пленённых
   точек и от клетки взятия, плюс сыгранный ход.
5. **Критерий спасения.** `minLoss <= captured/2`, и сыгранный ход хуже
   минимума хотя бы на 3 точки. Берётся **последний** ход бота перед взятием,
   для которого критерий выполнен.
6. **Спасающие ходы.** Это ходы с `loss <= minLoss + 1`; они сохраняются в
   поле `rescue`.
7. **Причина ошибки.** Её определяет функция `classifyMiss` по `trace`
   текущего поиска (классификация из #52):
   - `not-in-candidates` — ни один спасающий ход не попал в корневые кандидаты;
   - `width` — не попал, и при этом корневой список заполнен до
     `candidateCap`, то есть ход отрезан по ширине;
   - `time` — спасающий ход есть в кандидатах, но итеративное углубление
     остановлено бюджетом раньше `maxDepth`, то есть ход не исследован;
   - `misjudged` — исследован до `maxDepth`, но оценён хуже другого хода.

Источник позиций — только партии части `regression` манифеста S2
(`tools/bench/corpus/human/manifest.json`).

## Базовая доля спасений

Бюджет фиксирован через `nodeLimit`, поэтому результат детерминирован.

| Уровень | nodeLimit | Спасений | Причины ошибок |
|---|---|---|---|
| `normal` | 300 | **0/2** | width 1, time 1 |
| `strong` | 3000 | **0/2** | not-in-candidates 2 |

База записана в поле `baseline` набора. Вывод: на `strong` главная проблема —
генерация кандидатов. Спасающие ходы рядом с будущей сетью не попадают в
корневой список, и ни глубина, ни оценка тут не помогут. Это аргумент в пользу
S5/S6: кандидаты от монитора опасных групп.

## Тест

`test/replay-prefork.js` подключён в `npm test` и работает около 5 с. Тест
проверяет:

- каждая позиция взята из части `regression` манифеста, и в ней ходит бот;
- спасение существует: решатель пересчитывает потерю сыгранного хода и всех
  спасающих ходов, и результат совпадает с набором;
- поиск при фиксированном `nodeLimit` детерминирован (два одинаковых прогона);
- доля спасений не ниже базы. Допуска «минимум + 1» нет.

Если доля выросла, это улучшение. Тогда нужно перегенерировать набор
(`--prefork --game <id>` для каждой партии) и обновить таблицы выше.

## Ограничения

- Для спасающих ходов `forkLoss4` обрывался по бюджету `--fork-cap 40`, поэтому
  их потеря посчитана на 3 полухода (`measure: "twoMove"`), а не на 6.
  Потеря сыгранных ходов посчитана полным `forkLoss4` на 6 полуходов. Увеличить
  `--fork-cap` можно, но прогон станет заметно дольше.
- Набор маленький: 2 позиции. Его стоит пополнять по мере появления новых
  партий в `regression`.
