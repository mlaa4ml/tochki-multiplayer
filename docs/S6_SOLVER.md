# S6. Локальный решатель для угрожаемых групп (issue #60)

Часть дорожной карты #53, `docs/MONITOR_ROADMAP.md`, раздел S6. Код: `tools/bench/localSolver.js`. Тест: `test/local-solver.js`, входит в `npm test`, отдельный запуск — `npm run test:solver`. Решатель пока только инструмент: в выборе хода бота он не участвует, подключение — задача S7.

## Интерфейс

`solveGroup(node, def, target, opts)`:
- `node` — позиция, ходит защитник `def`;
- `target` — живые точки угрожаемой группы.

Варианты ответа:
- `{ saved: true, move }` — «спасение есть, лучший ход X»;
- `{ saved: false, move, loss }` — «группа потеряна, ожидаемая потеря N очков». `move` здесь — ход, который сильнее всего уменьшает потерю.

Дополнительно возвращаются `depth`, `nodes`, `verifyNodes`, `region` и `ms`.

## Метод

1. **Регион.** Пустые клетки в радиусе `radius` (по умолчанию 2) от точек группы, не больше `maxCells` (20). Порядок: ближние раньше, затем клетки с большим числом соседних точек группы, то есть выходы.
2. **Поиск.** Минимакс с альфа-бета и итеративным углублением по чётным глубинам до `maxDepth` (по умолчанию 10).
   - Защитник перебирает не больше `maxCand` (10) ходов региона: выходы и ходы, снимающие угрозу.
   - Атакующий играет только вынуждающие ходы: взятие точек группы или ход, после которого у него есть немедленное взятие, то есть угроза. Если вынуждающих ходов нет, позиция считается листом.
3. **Проверка найденного спасения.** Без неё «спасение» не выдаётся.
   - `verify`: после хода X атакующий перебирает **все** легальные ходы поля на `verifyDepth` полуходов.
   - `forkCheck`: та же структура, что у `forkLoss4` из #52, но по клеткам региона и только для точек группы. Атакующий отвечает, защитник защищается, затем атакующий ходит дважды подряд.
   - «Спасение есть» выдаётся, только если обе проверки дают нулевую потерю. Иначе ответ «потеряна», с потерей по лучшему кандидату.

Почему нужна проверка на вилку. Без неё на `issue52-r01-g0` решатель выбирал ход (7,3). Для этого хода `forkLoss4` даёт потерю 10, причём ответ (8,5) не закрывается никакой защитой на всём поле. Ограничение сети двухходовки 12 клетками тоже пропускало эту вилку. Сейчас сеть строится по всему региону.

## Корректность и полнота

Сверка с полным перебором выполнена так же, как в `test/candidates.js`:
- случайные позиции 5×5–6×6;
- угрожаемая группа — точки защитника, которые атакующий берёт одним ходом;
- эталон — минимакс по **всем** легальным ходам обеих сторон на 3 полухода после хода защитника.

Каждое «спасение есть» решателя перепроверяется этим перебором.

| Показатель | Значение |
|---|---|
| позиций с угрозой | 27 |
| спасение существует (перебор) | 25 |
| найдено решателем | 23 |
| **полнота** | **92.0%** |
| ложных спасений | **0** (корректность 100%) |
| ответов «потеряна» | 4 (2 из них — пропуски спасения из-за пессимистичной `forkCheck`) |
| среднее время | ~25 мс |

Без `forkCheck` полнота была 100% (25 из 25). Но тогда решатель ошибался на `regression`, см. ниже. Потеря полноты на 8 п.п. — осознанная цена: в `forkCheck` атакующий ходит дважды подряд, поэтому проверка пессимистична. Полнота измерена относительно горизонта перебора в 3 полухода. На более глубоком горизонте полный перебор на этих полях недоступен по времени.

## Время против общего поиска

На тех же позициях общий поиск (`searchMove`, strong, `maxDepth: 3`, без лимита узлов) доходит до глубины 3:
- `issue52-r01-g0` — за 1722 мс, ход (8,3), то есть зевок;
- `issue52-r02-g1` — за 906 мс, ход (1,2), тоже зевок.

Решатель за 110–270 мс проходит глубину 10 вместе с проверкой. Цель S6 «глубина 8–12 за время общего поиска до 3» выполнена.

## Параметры для S7

Запускать решатель по фильтру монитора `cost <= 2` (S5). Параметры по умолчанию: `radius: 2`, `maxCells: 20`, `maxCand: 10`, `maxDepth: 10`, `verifyDepth: 1`. `radius: 3` спасения на `regression` не меняет, но работает в 3–7 раз дольше (~800 мс).
