# S7. Арбитр и распределение времени (issue #61)

Часть дорожной карты #53 (`docs/MONITOR_ROADMAP.md`, раздел S7). Код: `arbiter.js`. Тест: `test/arbiter.js` (входит в `npm test`, отдельно — `npm run test:arbiter`).

## Флаг `monitor:false`

`arbiterMove(state, rows, cols, mover, diff, weights, opts)` имеет тот же интерфейс и формат ответа, что `gameEngine.searchMove`.

- `opts.monitor !== true` (по умолчанию) — арбитр возвращает **ровно** результат `searchMove` с теми же аргументами. Ход и `trace` совпадают с базой; при фиксированном `nodeLimit` это детерминированно и проверяется в `test/arbiter.js` (обе позиции `regression`, `monitor: undefined` и `monitor: false`).
- `opts.monitor === true` — включается арбитр. Это позволяет сравнивать версии парными матчами (S4/S8).

## Логика при `monitor:true`

1. Общий поиск `searchMove` с обычным лимитом (`diff.timeLimit`, 2–3 с).
2. Монитор `monitorPosition(node, mover)` без полного `twoMoveThreat` и без потенциала соперника (единицы мс). Тревога — группа бота с `cost <= alarmCost` (2, фильтр из S5/S6). Берутся не больше `maxGroups` (3) групп, крупные первыми.
3. **Дополнительное время идёт только на локальный решатель** `solveGroup` (S6) по тревожным группам. Бюджет — `alarmTimeLimit` (10 с), ограниченный сверху `maxAlarmTimeLimit` (настройка интерфейса, по умолчанию 20 с). Общий поиск дополнительного времени не получает.
4. **Спасение.** Решатель нашёл спасающий ход — бот играет его, если глобальная оценка хода (score из `trace.candidates` общего поиска) не хуже `bestScore - threshold` (`threshold` = 2). Если общий поиск этот ход не оценивал, ход принимается для групп от `minRescueSize` (2) точек.
5. **Ограничение ущерба.** Группа потеряна в любом случае — если ход общего поиска стоит рядом (8 соседей) с точкой потерянной группы и ничего не берёт, выбирается лучший по оценке кандидат вне групп (решение `avoid-lost`).

Решение пишется в `trace.arbiter`: `alarm`, `groups` (размер, cost, ответ решателя, оценка, принят ли), `decision` (`base` / `rescue` / `avoid-lost`), `overridden`, `budgetMs`, `monitorMs`, `localMs`, `timeout`.

## Интерфейс и сервер

- `public/client.html`: в комнате с ботом — чекбокс «Монитор групп (экспериментально)» (по умолчанию выключен) и поле «Предел при тревоге, с» (1–60, по умолчанию 20). Предел вынесен в интерфейс, потому что время зависит от устройства.
- `server.js`: `sanitizeRoomOptions` принимает `botMonitor` и `botAlarmLimitSec` (ограничение 1–60 с). При включённом мониторе запрос в пул идёт с `searchOpts = { monitor: true, maxAlarmTimeLimit, alarmTimeLimit: min(10 с, предел) }`. В деградированном режиме (`BOT_FALLBACK_OPTS`) арбитр не используется.
- `botWorker.js`: при `searchOpts.monitor === true` (только Node) вызывает `arbiterMove`, иначе — `searchMove` как раньше.

## Ограничения

- Арбитр работает только в Node (серверный бот). Монитор и решатель лежат в `tools/bench` и используют `process.hrtime`; в офлайн-версии и браузерном Worker флаг игнорируется.
- Жёсткий таймаут запроса при включённом мониторе расширяется автоматически: `server.js` передаёт в `botPool.search(msg, { key, timeoutMs })` значение `BOT_TIMEOUT_MS + botAlarmLimitSec * 1000`. Общий поиск укладывается в обычный таймаут пула, локальный поиск решателя — в предел из интерфейса. Поэтому предел 10–20 с (и до 60 с) реально используется, и `BOT_TIMEOUT_MS` поднимать не нужно. Запросы без монитора и деградированный режим по-прежнему ограничены `BOT_TIMEOUT_MS`.
- На `regression` (#57): на `issue52-r01-g0` монитор поднимает тревогу только по группе из 1 точки (`cost = 2`); решатель находит для неё спасение (0,3), но арбитр отвергает его по порогу оценки. Группа из 9 точек, которую нужно спасать ходом (8,5), по `cost` не попадает в фильтр `cost <= 2` — это известное ограничение монитора (S5). На `issue52-r02-g1` тревоги нет. Улучшение сигнала тревоги и выбор порогов — S8 (абляции, парные матчи).
